# printkit v0.1 — Design

**Date:** 2026-08-21
**Status:** Approved for planning (brainstorm complete, pending user sign-off on this doc before `writing-plans`).
**Supersedes/extends:** `docs/business/2026-08-18-printer-kit-initial-scope.md` (hardware/protocol research — stays the source of truth for NIIMBOT B1 technical detail, cited below rather than repeated) and `docs/business/2026-08-18-feature-discussion-per-kit.md` (Tier 0 roadmap item).

## Product identity

printkit is a **hardware print connector** for Merqo vendors — not a single-purpose "cup label app." The architecture is job-type-agnostic from day one so label, receipt, kitchen-ticket, shelf-label, and invoice printing can all live under one product without a later redesign. **v0.1 ships one job type (label, via the NIIMBOT B1)** with the plumbing built generically; later minors add job types incrementally. An official "v1" launch happens once integration breadth (multiple job types, proven with real vendors) is settled — v0.1 is a real, usable release, not a throwaway prototype.

**Internal Merqo product, not a standalone offering.** printkit is reached only through a vendor's existing relationship with a sibling kit (qkit today; paykit/stockkit as they adopt it) — there is no cold-acquisition funnel, no independent pricing, and `kit_api_keys` issues bearer secrets only to Merqo's own kits. Opening printkit to non-Merqo integrators is a possible future direction, not a current goal; revisit only if a real external-integration need shows up, same discipline as the other deferred items in this doc.

## Why now / origin

Vendors currently handwrite customer names/order numbers on cups for pickup identification. Manfred (real named design partner) is already testing a NIIMBOT B1 label printer independently. Full origin, hardware choice, and protocol research: `2026-08-18-printer-kit-initial-scope.md`.

## v0.1 scope boundary

**In scope, built end-to-end:**

- qkit → printkit job creation (order placed → label job queued) — testable today, no hardware needed.
- printkit's own data model, dashboard, job history, audit trail — testable today.
- The full Android-bridge pairing/print flow (Web Bluetooth, image rendering, job delivery) — **built now, verification deferred** to a real hands-on test with Manfred's physical B1 unit later. The code path exists and is exercised by non-hardware tests (unit tests on rendering logic, mocked Bluetooth in integration tests); the actual "does a real label come out correctly" check is a manual gate before calling v0.1 done, not before writing the code.

**Explicitly deferred to later minors** (not v0.1, but the architecture doesn't block them):

- Receipt/kitchen-ticket printing (ESC/POS — a genuinely different protocol/hardware track from label printing; needs its own hardware research when picked up).
- Shelf-label printing (stockkit's use case — waits for stockkit's own build to resume per the roadmap doc; likely reuses the label job-type path largely as-is once stockkit exists as a consumer).
- Invoice printing — needs its own scoping pass first to resolve whether this means a thermal receipt-style slip (ESC/POS track) or a full-page A4/letter document (a completely different problem — no Bluetooth/bridge needed at all, a browser can already generate/print a PDF directly). Not classified yet; classify when this minor is actually picked up.
- Native iOS app / any path that removes the second-device requirement — real trigger condition stated below, not proposed now.

## Architecture

**Stack/deployment**: matches every sibling kit exactly — Next.js + Supabase (`@supabase/ssr`), own `printkit` schema in the shared Supabase project, own Vercel deploy, called via bearer-secret HTTP API (`kit_api_keys` pattern, same as paykit's `/api/v1/*`). `@merqo/ui` for shared components (AccountMenu via a local wrapper, shadcn primitives) — same convention every kit already follows. No shared code library for the print/Bluetooth logic itself — that's printkit-only, never imported by another kit.

**One web app, two device roles** — no separate bridge server/Raspberry Pi (the cheaper, revised architecture from the 08-18 research, reconfirmed today after deep research into iOS alternatives — see "iOS / Bluetooth research" below):

- A vendor's iPad (or any device) opens printkit to configure the printer link, monitor job history, and view connection status. No Bluetooth needed here.
- A cheap Android phone (~S$70-180, Android 10+, Chrome kept current) sits next to the physical printer, running the _same app_ in an explicit vendor-toggled **"Bridge mode"**. This is the only device that ever touches Web Bluetooth.

**Job delivery to the bridge device**: Supabase Realtime, channel scoped to `vendor_id`. Reliability plan (see "Reliability" below) — this was a real research question, resolved with a documented pattern, not a hand-wave.

**Cross-kit integration direction**: qkit calls `POST /api/v1/print-jobs` (bearer-secret, same shape as paykit's kit-auth) on order-placed to create a job. printkit calls back into qkit with a small bearer-secret `POST` when a job's status changes (especially failure) — this direction was chosen after checking this portfolio's own real precedent (qkit's actual paykit integration has no production polling loop; the proven pattern for "kit B needs to tell kit A something happened" is the kit→kit callback already used twice for Telegram-notify). qkit surfaces a "print failed" badge on the relevant order from that callback.

## iOS / Bluetooth research (decided, not open)

Two research passes this session confirmed: iOS's Web Bluetooth block is current and unconditional (WebKit's own Standards Positions repo, issue closed "oppose," Nov 2025) and applies identically to a home-screen/PWA-installed web app — standalone display mode is still WebKit under the hood, no different API surface. Real alternatives were ranked and all lose to the Android-bridge design on this team's actual constraints (no dedicated iOS dev, no appetite for a $99/year recurring Apple Developer account, no capacity for a second codebase): native Swift+CoreBluetooth app, a Capacitor hybrid wrapper (still needs the same paid account for any real-device distribution), and a custom ESP32 BLE-to-WiFi bridge (cheap part, but no existing project actively drives a specific printer's protocol this way — real embedded firmware work from scratch).

**Decision: Android-bridge-device architecture, no native/hybrid app.** **Stated trigger condition for revisiting** (same discipline as every other deferred item in this portfolio): a real vendor explicitly refuses the second device and it costs a sale. Not before then.

## Reliability

Two real, researched failure modes, each with a documented (not improvised) mitigation:

- **Bridge device background throttling** (screen locks / app backgrounds → Bluetooth and Realtime both at risk). Mitigation: acquire the **Screen Wake Lock API** (Chrome Android 84+) the moment Bridge mode is toggled on; re-acquire on `visibilitychange` (it auto-releases on tab-switch). Onboarding requirement to state explicitly to vendors: disable Battery Saver on the dedicated bridge phone — wake lock doesn't override that.
- **Supabase Realtime silent disconnect on a backgrounded tab** (documented Supabase issue — background timer throttling kills the heartbeat after ~5 min). Mitigation: explicit `visibilitychange` handler that checks channel status and resubscribes on foreground — Supabase's own documented pattern for this, not a workaround.
- **Bridge online/offline signal**: Supabase Realtime **Presence** (channel scoped to `vendor_id`) for the live "is the bridge currently reachable" indicator — purpose-built for this, no extra table needed for v0.1. A persisted history table (e.g. "offline for 20 min at 3pm") is a real later addition, not needed now.
- **Print failure UX** (from the 08-18 research, reconfirmed as a v1 must-have, not deferrable): persistent Bluetooth connected/disconnected pill on the bridge device's own screen, an on-screen error toast on a failed print write, a "print failed" badge on the order in qkit's dashboard (via the callback above), and a manual reprint button. No automatic retry queue for v0.1 — visible failure + manual recovery is enough.

## Data model

- **`print_jobs`** — core table, also doubles as the vendor-facing job/transaction history (a vendor searching "what got printed for order #47"): `id`, `vendor_id`, `job_type` (`'label'` only in v0.1, column designed to hold future types), `payload` (jsonb — customer name/order # for v0.1), `status` (`queued`→`sent`→`printed`|`failed`), `source_kit` (`'qkit'`), `source_ref` (qkit's order id), `created_at`, `printed_at`.
- **`admin_audit`** — built in from day one (not retrofitted later, unlike the portfolio-wide audit-trail item still pending on the older kits), same immutable pattern every sibling kit already runs: service-role insert/select only, no update/delete grant even for service-role, RLS admin-read-only. Logs every disputable action: bridge connected/disconnected, printer paired, manual reprint triggered, qkit link connected/disconnected, print-job config changed.
- **`kit_api_keys`** — same bearer-secret pattern as paykit, for qkit's inbound calls.
- No persisted bridge-device table for v0.1 (Presence covers the live signal — see Reliability).

## Vendor-facing screens (reference, not restated)

Full draft flow already scoped in `2026-08-18-printer-kit-initial-scope.md` ("Vendor-facing webapp — draft screen architecture"): bridge/Bridge-mode toggle → auto-detected printer confirmation with real product photo → pairing with live status → test print (Square's literal copy pattern) → link to qkit (IFTTT-scope simplicity, not Zapier's field-mapping complexity) → status/history dashboard. Visual design pass sequenced after this spec, via `impeccable`/`frontend-design`, same order used for loopkit's own visual work — not part of this spec.

**Root route (`/`) is a redirect, not a landing page.** Because printkit has no cold-acquisition funnel (see "Internal Merqo product" above), `/` sends an authed vendor straight to `/dashboard` and an unauthed one to `/login` — no marketing hero, no pricing, no public pitch copy. This differs from qkit/paykit's own root pages, which are real standalone marketing landing pages for their own cold sign-up funnels.

## Explicitly out of scope for v0.1

- Any job type besides label.
- Any native/hybrid iOS app.
- Automatic print-retry queue (manual reprint only).
- Persisted bridge-device history table (Presence only).
- Multi-printer-brand support (NIIMBOT B1 only, stated plainly in onboarding copy per the 08-18 research's "Scope/support-boundary" finding — other printers not supported, not roadmapped without validated multi-vendor demand).
- Public marketing landing page, pricing/plans, and self-serve/external-integrator API access — printkit is internal-only (see "Internal Merqo product" above); `/` is a redirect, not a pitch page.

## Open items for the implementation plan (not blocking this spec)

- Exact image-rendering approach for the label bitmap (server-side vs client-side render of "customer name + order #" to the 384px-wide PNG NIIMBOT expects) — an implementation detail, not an architecture decision.
- Whether `niimblue`'s existing browser JS gets vendored/adapted directly or reimplemented against `niimbluelib`'s protocol docs — implementation-plan-level.
- Repo/subdomain bootstrapping specifics (scaffold via `templatecentral:scaffold`, Next.js Supabase variant, harness parity with sibling kits) — implementation-plan-level, not a design decision.
